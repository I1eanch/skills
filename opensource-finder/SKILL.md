# Opensource Finder

Скилл избавляет от повторного изобретения решений. Он ищет в GitHub и опенсорсе **уже пройденный путь** для конкретной инженерной задачи, оценивает силу доказательств и переносит сильнейший вариант в локальный код минимальной проверяемой правкой.

GitHub здесь — источник доказательств, а не список ссылок. Цель: описать локальную задачу, найти путь, который опенсорс уже прошёл (репозитории, issue, PR, обсуждения, примеры, release notes, исходники), оценить, подходит ли он этой кодовой базе, и адаптировать.

Область — только код и инженерия: баги, ошибки рантайма, падения сборки/тестов/деплоя, зависимости, использование фреймворков и API, блокеры интеграции, шаблоны реализации, выбор инструментов, адаптация опенсорсных решений.

## Когда применять

- Ошибки рантайма, сборки, тестов, деплоя, пакетов, SDK, API, зависимостей, фреймворков или интеграций.
- Реализация фичи встала из-за неясного edge-case, отсутствующего примера использования, поведения конкретной версии или непонятного контракта API.
- Локальная проблема похожа на то, что мейнтейнеры или другие пользователи уже решили в issue, PR, примерах, коде, release notes или обсуждениях.
- Спрашивают, решена ли конкретная инженерная задача в опенсорсе.
- Зрелые примеры реализации или готовый проект снизили бы неопределённость по одной конкретной возможности.
- Нужно сравнить подходящие репозитории и объяснить, как перенести один проверенный путь к себе.

Вне области: правки текста, чисто локальные рефакторинги, где ответ уже задан кодовой базой, некодовые задачи, и запросы с явным запретом на сеть или GitHub. Приватные репозитории смотреть только при явном разрешении и с очерченными границами.

## Рабочий процесс

1. **Сначала описать локальную задачу.** Цель, симптом, текст ошибки, путь воспроизведения, версии, рантайм, имена зависимостей и фреймворков, недавние изменения, ограничения и уже испробованные варианты. Если факт можно узнать самому — сначала прочитать локальные файлы и логи, потом спрашивать.
2. **Выбрать поверхность доказательств.** Для ошибок и регрессий — сперва issue, PR, релизы и код. Для потребности в возможности или инструменте — сперва репозитории-кандидаты. Для застрявшей реализации — и то, и другое.
3. **Оценить пользу от субагентов.** Решить, повысят ли они охват, качество доказательств или независимость проверки. Если субагенты не нужны, коротко назвать причину в отчёте о пути поиска.
4. **Составить точные запросы.** Точный текст ошибки, класс исключения, имя пакета и метода, номер версии, ключ конфигурации, фрагмент стектрейса, имя упавшей команды или связка «возможность + фреймворк/рантайм/API».
5. **Найти подходящие проекты, когда это уместно.** Приоритет — активные, не заархивированные репозитории с внятной лицензией и живыми примерами, точно попадающие в задачу. Порог по звёздам снижать, если выборка популярных проектов слишком широка или мимо задачи.
6. **Пройти по поверхностям доказательств.** Issue, PR, обсуждения, код, примеры, release notes и официальная документация проекта. Поиск по репозиториям обязателен, когда решением может быть сам проект.
7. **Ранжировать по попаданию в задачу; звёзды — сигнал зрелости.** Популярный репозиторий — сильный кандидат на осмотр, но подтверждение мейнтейнера, влитый PR, вышедший фикс, официальный пример и точно совпадающий код весят больше, чем популярный соседний проект. Когда ранжирование существенно, использовать [research-rubric.md](references/research-rubric.md).
8. **Глубоко прочитать сильнейших кандидатов.** По [extraction-playbook.md](references/extraction-playbook.md) извлечь основу проекта, переиспользуемые интерфейсы, первопричину или шаблон реализации, ограничения по версиям, риски, границы адаптации и шаги проверки.
9. **Перенести к себе минимальной адаптацией.** Сохранить проверенный поток, API, форму конфигурации или архитектуру там, где они подходят. Менять только то, что требуют локальные интерфейсы, конфигурация, модель данных и доступа, цель деплоя или язык и рантайм.
10. **Проверить до заявления об успехе.** Тесты, сборка, команда воспроизведения, реальный запрос, логи, проверка в браузере или ручной осмотр — по характеру задачи.
11. **Слабые доказательства называть слабыми.** Отмечать рекомендацию как вывод из первых принципов или чисто локальную, когда опенсорсных доказательств недостаточно.

## Инструменты

### В OMP — сначала нативные инструменты

OMP даёт кешируемый доступ к GitHub дешевле, чем внешний вызов. Порядок предпочтения:

| Задача | Инструмент OMP |
| --- | --- |
| Прочитать issue или PR с комментариями | `read issue://<N>`, `read pr://<N>`; чужой репозиторий — `pr://<owner>/<repo>/<N>` |
| Посмотреть дифф PR | `read pr://<N>/diff` — список файлов, `pr://<N>/diff/<i>` — срез по файлу, `pr://<N>/diff/all` — целиком |
| Поиск с фильтрами по датам и авторам | `xd://github`, `op: search_issues \| search_prs \| search_code \| search_commits \| search_repos`, поля `since`, `until`, `dateField` |
| Прочитать файл из репозитория GitHub | `xd://github`, `op: file_read` — обязательно вместо `curl` и `wget` |
| Забрать PR для локальной проверки | `xd://github`, `op: pr_checkout` — уходит в отдельный worktree, рабочее дерево не трогается |
| Прочитать документацию или статью по ссылке | `read <URL>` — reader-mode, чистый текст |
| Разобрать исходники библиотеки под вопрос | субагент `librarian` |
| Параллельное независимое исследование | `task` с `agent: scout`, одним батчем `tasks[]` |
| Найти вызовы и определения в локальном коде | `lsp` (references, definition), `grep`, `glob` |

### GitHub CLI как основа

`gh` остаётся основой поиска, когда нужны поля или фильтры, которых нет в нативных инструментах. Шаблоны как отправная точка — запрос, репозиторий, поля и лимиты подгонять под задачу:

```bash
gh search repos "<запрос>" --archived=false --sort stars --order desc --limit 10 --json fullName,url,description,stargazersCount,forksCount,language,license,pushedAt,isArchived,openIssuesCount
gh search issues "<запрос>" --repo owner/repo --sort updated --order desc --limit 10 --json title,url,state,updatedAt,commentsCount,repository,body
gh search prs "<запрос>" --repo owner/repo --merged --sort updated --order desc --limit 10 --json title,url,state,updatedAt,commentsCount,repository,body
gh search code "<запрос>" --repo owner/repo --limit 10 --json path,url,repository,sha
gh repo view owner/repo --json nameWithOwner,url,description,stargazerCount,forkCount,licenseInfo,primaryLanguage,pushedAt,repositoryTopics,homepageUrl
gh api -X GET search/repositories -f q='<запрос> archived:false' -f sort=stars -f order=desc
```

Собственные поисковые скрипты для этого скилла не нужны. `gh auth status` запускать только после отказа с 403, 429, ошибкой доступа к приватному репозиторию или явным сообщением о неавторизованности. При 403 или 429 сначала посмотреть контекст лимита, затем повторять с меньшим охватом или другим эндпоинтом.

## Параллельное исследование

Субагенты — условное подспорье, а не обязательный шаг. Контроллер остаётся ответственным за постановку задачи, границы охвата, ранжирование доказательств, локальную адаптацию и финальную проверку.

Субагенты полезны, когда выполняется хотя бы одно:

- задача покрывает 2+ независимых экосистемы, фреймворка, языка, инструмента, цели деплоя или сообщества;
- поиск кандидатов требует широкого охвата по нескольким семействам запросов;
- доказательства из issue, PR, обсуждений, кода, релизов и примеров делятся по проектам, версиям или поверхностям без пересечений;
- итоговая рекомендация выигрывает от независимой проверки доказательств, рисков или причин отклонения кандидатов.

Работать одному, когда: задача — узкая ошибка с одним очевидным пакетом, репозиторием или API; сначала нужно понять локальный контекст, логи, конфигурацию и воспроизведение; лимиты GitHub, границы доступа, приватные репозитории, секреты или продовые данные делают делегирование рискованным; субагенты дублировали бы одни и те же запросы или правили одни и те же файлы.

При использовании субагентов контроллер:

- задаёт каждому семейство запросов, область репозиториев, поверхность доказательств, ограничения, разрешённую область записи и ожидаемый результат;
- требует прямые ссылки, проверенные метаданные, обоснование попадания в задачу, заметки о рисках и явные причины отклонения;
- держит субагентов read-only, пока отдельная фаза реализации не выдаст узкую область записи;
- объединяет и дедуплицирует результаты до ранжирования: повторные сообщения об одном issue, PR, участке кода или репозитории — одно доказательство, не несколько;
- сам проверяет сильнейшие утверждения через `pr://`, `issue://`, `gh`, чтение исходников, тесты, логи, реальные запросы или официальную документацию.

## Стратегия поиска

- Начинать узко: точная строка ошибки, класс исключения, вывод CLI, пакет плюс имя метода, ключ конфигурации или фрагмент стектрейса.
- Добавлять ограничения: версия пакета и фреймворка, язык, платформа, цель деплоя, бандлер, база данных, провайдер аутентификации, рантайм.
- Порядок поверхностей: issue, PR и обсуждения → влитые фиксы → release notes и changelog → примеры и шаблоны → исходный код → репозитории-кандидаты.
- Для блокера реализации без ошибки искать нужную возможность вместе с именами фреймворка, рантайма и API.
- Для публичных платформенных данных — тренды, топы, поиск по темам, метрики вовлечённости — не начинать со скрейпинга браузером. Сначала искать переиспользуемые публичные эндпоинты, опенсорсные краулеры, архивные датасеты и доказательства о полях API; затем проверять выбранный источник минимальным реальным запросом и явно разделять анонимные топы и данные, доступные только под логином.
- Для поиска готового проекта сортировать репозитории по звёздам, затем глубоко читать только кандидатов, попадающих в задачу. Фиксировать звёзды, форки, язык, лицензию, активность и суть проекта.
- Понижать совпадения устаревшие, с расхождением версий, заархивированные, нерешённые, спекулятивные и основанные только на догадках пользователей.
- Звёзды и форки — контекст зрелости и способ разрешить ничью между равно подходящими репозиториями. Они не перевешивают попадание в задачу, подтверждение мейнтейнера, влитый PR, release notes, официальный пример и воспроизводимый код.
- Для безопасности, аутентификации, платежей, инфраструктуры и продовой эксплуатации сверять опенсорсные находки с текущей официальной документацией или официальным репозиторием.

## Стандарт доказательств

Для каждого серьёзного доказательства определить:

- точность совпадения: та же ошибка, поведение, API, версия, окружение или процесс;
- силу: подтверждение мейнтейнера, влитый PR, вышедший фикс, воспроизводимый пример, тестовая фикстура или повторные независимые сообщения;
- применимость: какие условия должны совпасть локально, чтобы решение сработало;
- ценность для реализации: патч, конфигурация, использование API, версия зависимости, процесс, тест или эксплуатационный шаблон, который стоит перенести;
- основу проекта, когда кандидат — репозиторий: имя, URL, звёзды, форки, язык, лицензия, активность, суть, обоснование попадания и цена адаптации;
- риск: устаревшая версия, нерешённый issue, небезопасный обходной путь, вопрос лицензии, влияние на безопасность и приватность, расхождение с целью деплоя, слишком широкая правка.

## Контракт вывода

Когда скилл существенно влияет на ответ, ответ содержит:

- профиль локальной задачи: цель, симптом или ошибка, версии и окружение, локальные ограничения;
- путь поиска: запросы или способы обнаружения, пройденные поверхности, и были субагенты задействованы или нет;
- трассу субагентов, если они использовались: область каждого, поверхности доказательств, ключевые находки, отклонённые кандидаты, результат дедупликации и какие утверждения контроллер проверил сам;
- кандидатов-проекты, когда решением может быть сам проект: ссылка, звёзды, форки, язык, лицензия, активность, суть, обоснование совпадения и способ применения локально;
- ключевые доказательства: ссылки на issue, PR, код, примеры, релизы или репозитории с обоснованием совпадения;
- рекомендацию: что переиспользовать напрямую, что адаптировать локально, что не копировать и почему это подходит;
- отклонённые и рискованные варианты с причиной;
- стандарт проверки: тест, сборка, команда воспроизведения, реальный запрос или ручная проверка, подтверждающая починку;
- метку уверенности, когда доказательства слабы или сильного опенсорсного решения не нашлось.

Когда решением может быть репозиторий, добавить компактную таблицу проектов. Для чистых фиксов из issue, PR или кода таблица опциональна, но контекст репозитория стоит указать, если он влияет на доверие или применимость.

Ответ должен содержать доказательства, а не только ссылки, звёзды и рейтинги популярности. Формулировку «распространённый шаблон на GitHub» подкреплять ссылкой. Локальные ограничения имеют приоритет над внешними примерами.

Для кандидатов из области сайтов, SaaS, лендингов, тем и фронтенд-шаблонов приводить и ссылку на репозиторий, и ссылку на живое демо. Если демо нет или он не проверен — сказать это прямо и понизить кандидата.

## Границы безопасности

- Переиспользовать публичные интерфейсы, форму конфигурации, процессы, шаблоны тестов и архитектурные идеи; при переносе самого кода сначала проверять лицензию и требования к указанию авторства, держа эти обязательства на виду.
- Сохранять проверенный поток опенсорсного решения целым и вносить только те локальные адаптации, которых требует задача; большие переписывания апстрима — отдельное решение с обоснованием.
- Пересказывать своими словами, цитаты держать короткими: длинные дословные выдержки из репозиториев, README, issue, PR и документации не переносить.
- Исследовать публичный GitHub. Приватные репозитории — только по явному разрешению пользователя и в очерченных границах.
- Токены GitHub, cookie, пароли, ключи API, содержимое приватных репозиториев, внутренний контекст, чувствительные логи, продовые данные и учётные данные держать вне промптов, вывода, логов, файлов скилла, памяти и заданий субагентам.
- Когда сети нет, сказать, что опенсорсное исследование выполнить не удалось, и отметить рекомендацию как чисто локальную.
