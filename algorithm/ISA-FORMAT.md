# ISA проекта — формат

`<project>/ISA.md` — живой список утверждений о системе. Каждое утверждение проверяется командой, которую запускает `isa-check.ts`. Файл лежит в git проекта и переживает любые прогоны: задача добавляет утверждения, которые пока не выполняются, и закрывается, когда они проходят.

Здесь то, что система **гарантирует**. Как работать с репо — это `AGENTS.md`; модульная логика — это тесты, ISA на них ссылается.

## Пример

```markdown
---
isa: "1"
project: healthschool-os
updated: 2026-09-24
---

# ISA — healthschool-os

## Доступ к данным
- [x] ISC-12: Анонимный пользователь не читает twin_objects
  probe: psql "$TEST_DB_URL" -c "set role anon; select 1 from twin_objects limit 1"
  expect: fail /permission denied/

## Сборка
- [x] ISC-30: Типы проекта собираются без ошибок
  probe: pnpm tsc --noEmit
  timeout: 180

## Прод
- [x] ISC-40: Health endpoint прода отвечает 200
  probe: curl -s -o /dev/null -w '%{http_code}' "$PROD_URL/api/health"
  expect: stdout /^200$/
  env: prod

## Почта
- [ ] ISC-50: Письмо сброса пароля выглядит аккуратно на мобильном
  probe: manual
```

## Утверждение

Строка критерия — как в PRD: `- [ ] ISC-N: текст`, `- [x] …`, `- [DEFERRED-VERIFY] …`; удалённое — `- [ ] ISC-N: [DROPPED — причина]`. ID стабильны, разбиение даёт `ISC-N.M`. Раздел `## …` — подсистема; им можно фильтровать запуск.

Поля — строками с отступом под критерием:

| Поле | Значение | По умолчанию |
|---|---|---|
| `probe:` | shell-команда из корня проекта, или `manual` | — обязательно |
| `expect:` | `exit 0` · `fail` · `fail /re/` · `stdout /re/` | `exit 0` |
| `env:` | `test` или `prod` | `test` |
| `timeout:` | секунды | `60` |

- `fail /re/` — команда должна упасть, а stdout+stderr совпасть с шаблоном. Так проверяются запреты: RLS, права, валидация.
- `stdout /re/` — код 0 и stdout (без концевых переводов строк) совпадает с шаблоном.
- `manual` — раннер не запускает, а перечисляет отдельно. Оставляй только для оценок на вкус; остальное автоматизируется: почтовый ящик через API, UI через Playwright-скрипт проекта.

`[x]` означает «подтверждено и должно оставаться правдой». `[ ]` — ещё не выполняется: цель будущей задачи.

## Правила проверок

- **Только чтение.** Проверка не пишет в БД, не меняет файлы проекта, не деплоит. Всё, что изменяет систему, живёт в тестах и скриптах проекта, а ISA вызывает их read-only-режим. Нарушение правила — дефект ISA, его ловят на ревью как дефект кода.
- **Секреты — через переменные.** Раннер подмешивает `.env` и `.env.local` из корня проекта в окружение команд; значения в `ISA.md` не пишутся.
- **Prod — только явно.** Утверждения `env: prod` запускаются только с `--env prod` или `--env all`.
- **Одна проверка — один ответ да/нет.** Если утверждение нельзя проверить одной командой, его разбивают.

## Запуск

```bash
bun ~/.omp/agent/skills/algorithm/isa-check.ts <project>/ISA.md [--env test|prod|all] [--only ISC-12,Сборка] [--baseline <report.json>] [--jobs 4] [--json] [--verbose]
```

В OMP то же самое — команда `/isa-check [аргументы]` из любой папки проекта.

- Вывод — одна строка итога, провалы с хвостом вывода, список `manual`, путь к отчёту. `--verbose` добавляет прошедшие.
- `--only` принимает ID и названия разделов через запятую; неизвестное имя — ошибка аргументов. В `/isa-check` раздел с пробелами берётся в кавычки: `--only "Сборка и качество"`.
- С `--baseline` раннер сравнивает с прошлым отчётом: `РЕГРЕССИИ` — проходило, а теперь падает; `не перепроверены` — проходило, а в этом прогоне не запускалось (отфильтровано `--only`, пропущено по `env`). Поэтому финальный прогон задачи — всегда по всему ISA.
- Отчёт — `.isa/runs/<время>.json` и `.isa/last.json`; каталог `.isa/` игнорирует сам себя.
- `ISA.md` раннер не изменяет: галочки ставит Algorithm в рамках задачи.
- `Отмечены [x], но не проходят` — утверждение, которое система перестала выполнять. Это либо регрессия, либо устаревшее утверждение; в обоих случаях — работа.
- Код выхода: `0` — провалов нет, `1` — есть провал, регрессия или неперепроверенное утверждение, `2` — ошибка формата или аргументов.

## Как завести ISA для проекта

1. Собери 15–30 утверждений из того, что проект уже гарантирует: ADR, закрытые issues, инварианты БД и RLS, сборка и тесты, health прода.
2. Для каждого — read-only проверка; прогоняй `isa-check` по ходу и чини формат до кода `0` или честных провалов.
3. Проваленные утверждения, которые система действительно не выполняет, оставь `[ ]` — это бэклог.
4. Закоммить `ISA.md` в репо проекта вместе с правкой `AGENTS.md`: одна строка «гарантии системы — в ISA.md».
