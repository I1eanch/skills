# Algorithm 4.1-omp

Algorithm переводит систему из текущего состояния в целевое через проверяемые **критерии** и **доказательства**. PRD — журнал прогона: что пользователь попросил дословно, что должно стать правдой, чем это доказано и чем прогон закончился.

Прогон ведёт главный агент, и только он пишет PRD. Subagent получает в задании свой срез критериев и возвращает доказательства; главный агент переносит их в PRD.

Версия `4.1-omp` — ветка для OMP. Она выросла из PAI Algorithm v3.7.0, правила о доказательствах, воспроизведении, class-sweep, baseline, prerequisites и ревьюере адаптированы из [danielmiessler/LifeOS](https://github.com/danielmiessler/LifeOS) Algorithm v8.20.2 (MIT). Суффикс `-omp` отличает её от upstream v4.x.

## Вывод пользователю

- При входе — одна строка: `Algorithm 4.1-omp · <effort> · <slug>`.
- По ходу — короткий прогресс только тогда, когда он несёт факт.
- В финале — результат, путь к PRD, итоговая `phase` и `verified_by`.

## Шаги

### 1. Observe

1. Прочитай последние 5 строк `~/.claude/MEMORY/LEARNING/REFLECTIONS/algorithm-reflections.jsonl` и выпиши уроки, которые относятся к задаче. Если работа касается репозитория с engineering-loop, дополнительно возьми последние записи `"source":"engineering-loop"` с этим `loop_repo`.
2. Запиши цель пользователя **дословно** в `stated_goal`: одна строка в кавычках, цитата из его сообщения. Меняется она только по его явной правке. Критерии выводятся из неё.
3. Разбери запрос: что явно просили, что явно исключили, что очевидно нежелательно, насколько срочно. Если ответ на вопрос меняет то, что будет построено, задай до 3 точечных вопросов до начала работы; упомянутый, но не найденный предмет («то видео», «как обсуждали») найди в источниках или спроси.
4. **Prerequisites.** Проверь внешние зависимости до работы: токены, логины CLI, доступ к сервисам и БД, цели деплоя, квоты. Запиши их в `### Prerequisites` со статусом `OK`, `MISSING` или `UNKNOWN`. `MISSING` блокирует Execute, пока доступ не появится или пользователь не согласует отсрочку.
5. **Reproduce first.** Для бага сначала получи воспроизведение — вывод команды, `curl -i`, скриншот, `SELECT`, текст ошибки из лога — и только потом читай подозрительный код. Запиши его в `### Reproduction`.
6. **ISA проекта.** Если в корне проекта есть `ISA.md`, сними baseline прогоном всего ISA, без `--only`: `bun ~/.omp/agent/skills/algorithm/isa-check.ts <project>/ISA.md`. Запускай его в фоне (`bash` с `async: true`) и продолжай Observe и Plan: результат нужен только к началу Execute. Читай только раздел, который затрагивает задача. Абсолютные пути ISA и отчёта — во frontmatter `isa:` и `isa_baseline:`. Подробности — раздел «ISA проекта» ниже.
7. Выбери effort по таблице ниже и создай `~/.claude/MEMORY/WORK/<YYYYMMDD-HHMMSS>_<slug>/PRD.md` с frontmatter из раздела «Формат PRD», `phase: observe`.

Готово, когда PRD существует, `stated_goal` записана, prerequisites проверены, а для бага есть воспроизведение.

### 2. Plan

1. Запиши критерии в `## Criteria`. Критерий — **наблюдаемый результат** в мире после работы, у которого есть один инструмент-проверка из таблицы доказательств. Одно проверяемое утверждение на критерий, 8–14 слов.
2. Критерии проверяют систему, над которой идёт работа. Формат собственных артефактов (промпт субагенту, отчёт, сам PRD) — это ход работы, его в критерии не пишут.
3. Anti-criteria `ISC-A<n>` фиксируют то, что должно остаться нетронутым: данные, прод без явного OK, чужие изменения.
4. **Sweep-задачи** (переименовать, удалить, обновить версию, мигрировать, пройтись по всем X): перечисли цели одним `grep`/`glob` сейчас. Вывод команды и есть список, из которого строятся критерии.
5. **Baseline.** Если работа заменяет, перенаправляет или удаляет то, что обслуживает живой трафик или даёт метрику, до изменения сними baseline (частота событий, число строк, ответ endpoint) и добавь критерий паритета: после изменения поток на уровне baseline в оговорённом допуске. Один синтетический запрос паритет не доказывает. Для destructive-операций перечисли ресурсы через API провайдера до операции и повтори перечисление после.
6. Риски и premortem — в `### Risks`; для advanced и deep технический план — в `### Plan`.
7. Обнови `phase: plan`, `progress: 0/N`.

Готово, когда каждое явное требование пользователя покрыто хотя бы одним критерием.

### 3. Execute

1. `phase: execute`. Работай инструментами OMP: `task` для независимых срезов, `skill://…` для профильных процедур, `lsp` и `ast_edit` для кода.
2. Отмечай критерий `[x]` в той же правке, где добавляешь его доказательство в `## Verification`, и сразу обновляй `progress`.
3. **Class-sweep.** Если найденный дефект — представитель класса, одним `grep`/`glob` найди все однотипные места до закрытия и запиши в `## Decisions`: `CLASS-SWEEP: <класс> — N мест через <команда>; M исправлено, K отклонено с причиной`.
4. Новые сведения по ходу — правки пользователя, упавшие проверки, найденные ограничения — сразу превращаются в правку критериев. PRD в конце отражает то, чем «готово» оказалось на самом деле.
5. **Delegate liveness.** Задание субагенту — такого размера, чтобы его потеря стоила немного. Субагент замолчал без результата — один пинг через `hub`; снова тишина — он считается упавшим, это пишется в PRD, и на его отчёт не закрывается ни один критерий.
6. **Smart zone.** Качество рассуждений падает задолго до конца контекстного окна, ориентир ~100k токенов. Приближаясь к нему, закрой связный кусок работы, обнови PRD и продолжи в новой сессии из PRD вместо протягивания через compaction.
7. Нетривиальные решения и отклонения от плана — в `## Decisions`.

Готово, когда каждый критерий либо отмечен с доказательством, либо известна причина, по которой он недостижим.

### 4. Verify

1. `phase: verify`. Для каждого `[x]` в `## Verification` есть строка `ISC-<n>: <команда | файл | URL> → <наблюдённый результат>`, полученная в этом прогоне инструментом из таблицы доказательств.
2. **Attestation** обязательна для advanced и deep, а также для любого прогона с production-действиями или необратимыми операциями. Проверяет не автор:
   - subagent `reviewer`, запущенный заново, а не форк текущего контекста: форк унаследовал рассуждения автора и защищает его работу. В задании ревьюеру заново перечисли `stated_goal`, критерии, путь к PRD и diff;
   - `xd://loop_validate`, если работа идёт в engineering-loop;
   - пользователь, если проверка требует его доступа.
3. Запиши во frontmatter `verified_by: reviewer:<id>`, `loop_validate` или `user`. Когда изменение прошло через engineering-loop, `verified_by: loop_validate`, и кроме дословной цели и `## Ask Check` PRD хранит `loop_repo` (абсолютный путь к основному чекауту репозитория) и `loop_commit` (SHA кандидата, подтверждённого `loop_validate`): guard проверяет цепочку evidence → attestation → review этого прогона. Имя каталога прогона — сам токен и в PRD не записывается.
4. **ISA проекта.** Если задан `isa:`, прогони весь ISA, без `--only`: `isa-check.ts <isa> --baseline <isa_baseline>`, и запиши путь отчёта в `isa_final:`. Всё, что проходило в baseline, должно проходить и сейчас: упавшее — регрессия, не запущенное — «не перепроверено»; и то и другое блокирует `complete`: чини или объясняй в `## Outcome` с `partial`. Утверждения ISA, которые задача довела до выполнения, отметь `[x]` в самом `ISA.md`.
   Запускай этот прогон в фоне (`bash` с `async: true`) и параллельно делай attestation и Ask Check: проверки с неизменёнными `inputs:` берутся из кеша, долго идут только затронутые задачей.
5. **Ask Check** — последняя проверка перед закрытием. Перечитай сообщение пользователя дословно и внеси в `## Ask Check` каждую явную просьбу, включая указания о глубине («подробно», «быстро»):
   - `- ✓ «цитата» → где сделано`;
   - `- ✗ «цитата» — что не сделано`;
   - `- SKIP «цитата» — причина, согласованная с пользователем`.
   Любой `✗` не даёт закрыть прогон как `complete`. Формулировку критерия, которая не прошла, не смягчают, чтобы он прошёл.

Готово, когда каждый отмеченный критерий подтверждён, регрессий ISA нет, Ask Check без `✗`, а у прогонов, где нужна attestation, заполнено `verified_by`.

### 5. Close

Прогон заканчивается терминальной фазой в том же сеансе:

| phase | когда |
|---|---|
| `complete` | все критерии отмечены и подтверждены, Ask Check без `✗` |
| `partial` | часть сделана, остаток осознанно отложен |
| `blocked` | нужен внешний вход: решение, доступ, квота |
| `abandoned` | пользователь сменил направление или задача потеряла смысл |

Для `partial`, `blocked` и `abandoned` заполни `## Outcome`: что сделано, что нет, что нужно для продолжения. Затем добавь рефлексию.

Готово, когда `phase` терминальная и строка рефлексии записана.

## ISA проекта

`<project>/ISA.md` — живой список гарантий системы с командой-проверкой у каждого утверждения; формат, правила проверок и как завести ISA для проекта — в [`ISA-FORMAT.md`](ISA-FORMAT.md). Раннер `isa-check.ts` выполняет проверки без модели и не меняет `ISA.md`; в OMP его запускает команда `/isa-check`.

В прогоне Algorithm по проекту с ISA:

- Observe — baseline всего ISA (шаг 1.6), читается только затронутый раздел.
- Plan — утверждения ISA, которые задача меняет или добавляет, попадают в критерии PRD; новые утверждения сразу пишутся в `ISA.md` со статусом `[ ]` и read-only проверкой.
- Verify — финальный прогон всего ISA с `--baseline` (шаг 4.4): без регрессий и без неперепроверенных утверждений. `--only` — для быстрых промежуточных прогонов во время работы.

В прогоне по проекту без ISA этот раздел не применяется.

## Доказательства

| Что утверждает критерий | Чем доказывается |
|---|---|
| файл записан | `read` нужного диапазона |
| код изменён | `grep` нового символа или `read` диапазона, `lsp` diagnostics |
| команда работает | запуск команды и проверенный вывод |
| HTTP/API | `curl -i`: статус и форма тела |
| деплой | живой запрос к развёрнутой версии, сверка строки версии |
| UI | `browser`: скриншот или `observe` целевой страницы |
| БД | `SELECT`, подтверждающий запись или миграцию |
| конфиг, env | обратное чтение значения с диска или из сервиса |
| поток, метрика | частота относительно baseline за окно наблюдения |

Доказательство **покрывает** утверждение целиком: проверка контейнера (страница открылась, suite прошёл) не доказывает его элементы — проверь каждый тип элемента, который потребляет пользователь. Доказательство берётся **у источника истины**: состояние за кешем проверяется у authority, а не прогретым кешем сразу после изменения. Фразы «должно работать», «изменение на месте», «ошибок нет» без вывода инструмента доказательством не являются.

Если живая проверка сейчас невозможна (деплой ждёт окна, нужен доступ пользователя), критерий получает статус `[DEFERRED-VERIFY]`, а в `## Verification` — строку с `follow-up: <ID задачи>`. Отмеченным `[x]` он становится только после этой проверки.

## Effort

| effort | когда | критериев | бюджет |
|---|---|---|---|
| `standard` | ограниченная задача, 1–3 файла или одна система | 4–12 | ~15 мин |
| `advanced` | многофайловая или многосистемная работа, продакшен | 10–30 | ~60 мин |
| `deep` | архитектура, миграции данных, несколько репозиториев | 20–60 | ~3 ч |

Число критериев — ориентир, а не норма: достаточно, чтобы каждое требование пользователя было покрыто.

## Формат PRD

```yaml
---
algorithm: "4.1-omp"
task: <одна строка>
stated_goal: "<цитата из сообщения пользователя>"
slug: <YYYYMMDD-HHMMSS_kebab-slug>
effort: standard | advanced | deep
phase: observe | plan | execute | verify | complete | partial | blocked | abandoned
progress: <отмечено>/<всего>
started: <ISO 8601>
updated: <ISO 8601>
verified_by: <reviewer:<id> | loop_validate | user>
loop_repo: <абсолютный путь к основному чекауту репозитория, при verified_by: loop_validate>
loop_commit: <SHA кандидата из loop_validate, при verified_by: loop_validate>
isa: <абсолютный путь к ISA.md проекта, если он есть>
isa_baseline: <абсолютный путь к отчёту isa-check до работы>
isa_final: <абсолютный путь к отчёту isa-check --baseline перед закрытием>
---
```

Разделы по мере заполнения: `## Context` (с `### Prerequisites`, `### Reproduction`, `### Risks`, `### Plan`), `## Criteria`, `## Decisions`, `## Verification`, `## Ask Check`, `## Outcome`.

Критерии:

- `- [ ] ISC-1: …` — открыт; `- [x] ISC-1: …` — подтверждён; `- [DEFERRED-VERIFY] ISC-1: …` — ждёт проверки по follow-up;
- `- [ ] ISC-A1: …` — anti-criterion;
- ID стабильны: при разбиении критерий получает дочерние `ISC-3.1`, `ISC-3.2`; удалённый остаётся строкой `- [ ] ISC-4: [DROPPED — см. Decisions]` и выпадает из счёта.

`progress` считает только `[x]` из всех критериев кроме `[DROPPED`.

## Guard

Extension `algorithm-guard` (исходник `extension/algorithm-guard.ts` этого скилла, symlink в `~/.omp/agent/extensions/`) проверяет каждую запись PRD с `algorithm: "4.1-omp"`:

- есть `stated_goal` и остальные обязательные поля;
- ID критериев не повторяются;
- `progress` равен числу `[x]` из общего числа живых критериев;
- `complete` требует: все живые критерии `[x]` или `[DEFERRED-VERIFY]`, каждый id встречается в `## Verification`, у каждого `[DEFERRED-VERIFY]` есть `follow-up:`, `## Ask Check` непустой, у каждой строки статус ✓ / ✗ / SKIP и нет ни одного ✗;
- при `verified_by: loop_validate` (на любом effort) — `loop_repo` и `loop_commit` и валидная цепочка артефактов прогона: `evidence.json` с `passed`, `attestation.json` (PASS), `review.json` (approved) и `review-attestation.json` (APPROVED), где каждый хеш — sha256 байтов заверяемого файла, а `candidateCommit` — `loop_commit`;
- `complete` для advanced и deep требует `verified_by` от проверяющего, не от автора;
- `partial`, `blocked` и `abandoned` требуют непустой `## Outcome`.
- если задан `isa:` — `complete` требует `isa_baseline` и `isa_final`: абсолютные пути к существующим отчётам с того же ISA, оба сняты по всему ISA без `--only`, `isa_final` снят позже и с `--baseline isa_baseline`, регрессий и неперепроверенных утверждений нет.

Нарушение возвращается ошибкой инструмента: исправь PRD и повтори запись. Команда `/algorithm-doctor` показывает незакрытые прогоны, невалидные PRD и посторонние файлы в `MEMORY/WORK`.

### Подсказки

Guard добавляет к результату инструмента строку `algorithm-guard (подсказка): …` — вопрос о состоянии, которого нет в контексте модели. Подсказка не блокирует вызов и не делает результат ошибкой; главный агент получает её, subagent и Advisor — нет.

- **После разрушающей операции без активного PRD** — SQL `DROP`/`TRUNCATE`/`DELETE` через клиент БД, `git push --force` или удаление ветки, удаление через `gh`, `curl -X DELETE`, `supabase db reset`, удаление инфраструктуры, MCP-инструменты `…delete…`/`…archive…`. Вопрос: что принадлежало ресурсу по authority, перечислено ли это заново и держится ли поток на baseline. Один раз на тип операции за сессию.
- **Длинная сессия без PRD** — 60 вызовов инструментов или 8 изменённых файлов (`ALGORITHM_NUDGE_CALLS`, `ALGORITHM_NUDGE_FILES`) при отсутствии активного PRD. Вопрос: задача всё ещё мелкая или «готово» пора записать. Один раз за сессию.

Ответ на подсказку — действие: перечислить ресурсы и проверить поток либо завести PRD. Если причина её не применять очевидна, продолжай без комментария.

## Рабочая папка

`~/.claude/MEMORY/WORK/` хранит только папки прогонов `<YYYYMMDD-HHMMSS>_<slug>/` с PRD и доказательствами. Бэкапы, выгрузки и копии конфигураций кладутся в `~/.claude/MEMORY/BACKUPS/`. Секреты в PRD и логах маскируются как `***`.

## Рефлексия

Добавь одну строку в `~/.claude/MEMORY/LEARNING/REFLECTIONS/algorithm-reflections.jsonl`:

```json
{"timestamp":"<ISO 8601>","algorithm":"4.1-omp","effort_level":"<effort>","task_description":"<task>","prd_id":"<slug>","phase":"<терминальная phase>","criteria_count":0,"criteria_passed":0,"criteria_failed":0,"implied_sentiment":0,"within_budget":true,"reflection_q1":"<что стоило сделать иначе>","reflection_q2":"<как сработал бы более умный процесс>","reflection_q3":"<какой инструмент или скилл стоило задействовать>"}
```

Урок формулируй как конкретное действие для следующего прогона.

В этот же журнал пишет engineering-loop: `loopctl` сам добавляет строку `"source":"engineering-loop","event":"stalled"` (сигнал провала без токена), а координатор loop после `finalize` или `stalled` — строку с `reflection_q1..q3`. У таких строк нет `algorithm` и `prd_id`; связь с PRD — через `loop_repo`/`loop_commit`. Если PRD закрыт с `verified_by: loop_validate`, отдельную строку loop не дублируй: одной рефлексии Algorithm достаточно.

## Восстановление после compaction

Текущий прогон — самый свежий по mtime PRD в `~/.claude/MEMORY/WORK/` с нетерминальной фазой. Frontmatter даёт цель, фазу и прогресс, `## Criteria` и `## Verification` — состояние работы. Пройденные проверки не повторяются.
