# Многоракурсный веб-ресёрч

Скилл задаёт дисциплину сбора информации. Главный принцип: **один поисковый запрос — это никогда не исследование**, а качество любого текста ограничено качеством сбора, который ему предшествовал.

## Место среди других скиллов

| Скилл | Когда он, а не этот |
|---|---|
| **этот** | нужен структурированный сбор фактов за один проход: обычно 5–15 запросов и несколько прочитанных источников. Рабочая лошадка для подготовки отчёта, заметки, лендинга |
| `hyperresearch` | нужен глубокий многораундовый разбор с аудитом выводов, часы работы, тир-адаптивный конвейер |
| `research` | результат надо оформить файлом-исследованием в репозитории и делегировать фоновому агенту |
| `systematic-literature-review` | источник — научные статьи arXiv, нужен обзор литературы с цитированием |
| `github-deep-research`, `opensource-finder` | предмет — репозиторий, библиотека или инженерное решение |

Этот скилл — стандартный поставщик данных для `consulting-analysis`: его фаза 1 выдаёт готовые поисковые запросы с приоритетами P0/P1/P2, и они исполняются здесь.

## Инструменты этого инстанса

- **Поиск** — `web_search`. Поддерживает операторы: `site:`, `-site:`, `after:`/`before:` в формате `YYYY-MM-DD`, `inurl:`, `intitle:`, `filetype:`, `"точная фраза"`, `-исключение`, `OR`.
- **Чтение источника целиком** — `read` по URL (в оригинале это назывался `web_fetch`). Возвращает очищенный текст; `:raw` даёт исходный HTML. Читать источник, а не сниппет — обязательный шаг, а не опция.
- **Страницы, требующие JS или авторизации** — `browser`.
- **Параллельные ветки** — когда измерений много и они независимы, разослать их субагентам одним вызовом `task` с массивом `tasks[]`, агент `scout`. Одна ветка — один субагент, каждому явно указать, какие именно факты он должен вернуть и с какими ссылками.
- **Текущая дата** берётся из системного контекста (строка `Today:`), а не из памяти модели.

## Методология

### Фаза 1. Широкая разведка

1. **Обзорный проход** — 2–3 запроса по теме целиком, чтобы понять ландшафт.
2. **Выделение измерений** — из результатов вытащить подтемы, участников, точки зрения.
3. **Карта территории** — зафиксировать, кто и что утверждает, где расходятся оценки.

```
Тема: «онлайн-образование в нутрициологии, Россия»
Обзорные запросы:
- «рынок онлайн-образования Россия объём 2026»
- «онлайн-курсы нутрициология спрос»
- «дополнительное профессиональное образование статистика»

Выявленные измерения:
- объём и динамика рынка ДПО
- конкуренты и их продуктовые линейки
- регулирование образовательной деятельности и лицензирование
- поведение покупателя: мотивация, цикл принятия решения
- каналы привлечения и их стоимость
```

### Фаза 2. Углубление

По каждому важному измерению:

1. **Точные запросы** — узкие формулировки под конкретную подтему.
2. **Несколько формулировок** — синонимы, отраслевой жаргон, английский вариант, если тема международная.
3. **Чтение целиком** — `read` по URL на всё, что выглядит авторитетным: сниппет не содержит ни методики, ни оговорок.
4. **Ход по ссылкам** — если источник ссылается на первичное исследование, идти к первичному.

### Фаза 3. Разнообразие свидетельств

Собрать разные **типы** информации, а не больше однотипной:

| Тип | Зачем | Формулировки |
|---|---|---|
| Цифры и факты | доказательная база | «объём рынка», «статистика», «доля», «средний чек» |
| Кейсы и примеры | как это работает на практике | «кейс», «пример внедрения», «опыт» |
| Мнения экспертов | взгляд отрасли | «интервью», «экспертный разбор», «мнение» |
| Тренды и прогнозы | куда движется | «тренды 2026», «прогноз», «что изменится» |
| Сравнения | контекст и альтернативы | «сравнение», «vs», «альтернативы» |
| Критика и ограничения | сбалансированность | «проблемы», «риски», «критика», «почему не работает» |

### Фаза 4. Проверка перед выводами

- Тема просмотрена минимум с 3–5 разных ракурсов?
- Ключевые источники прочитаны целиком, а не по сниппетам?
- Есть конкретные цифры, есть примеры, есть позиция экспертов?
- Собраны не только достижения, но и ограничения с критикой?
- Данные актуальны, источники авторитетны?
- Каждое утверждение, которое пойдёт в текст, привязано к конкретной ссылке?

Любое «нет» — сбор продолжается.

## Формулировка запросов

```
# Конкретика вместо общих слов
✗ «тренды ИИ»
✓ «внедрение ИИ в корпорациях 2026 статистика»

# Указание на авторитетный тип источника
«<тема> исследование»
«<тема> отчёт»
«<тема> отраслевая аналитика»

# Ограничение по времени и площадке
after:2026-01-01
site:rbc.ru
filetype:pdf
```

Про даты: сначала посмотреть текущую дату в контексте, затем выбрать нужную точность. «Сегодня» и «только что вышло» требуют день и месяц в запросе, «недавно» — месяц, «в этом году» — год. Запрос только с годом не выдаст сегодняшних новостей.

## Планка качества

Сбор достаточен, когда можно уверенно ответить: какие ключевые цифры, какие 2–3 реальных примера, что говорят эксперты, куда движется тема, в чём ограничения и почему это важно сейчас.

## Типичные ошибки

- Остановиться после одного-двух запросов.
- Опираться на сниппеты, не открыв источник.
- Исследовать один аспект многогранной темы.
- Игнорировать противоречащие данные и критику.
- Брать устаревшие цифры, когда есть свежие.
- Начать писать текст до окончания сбора.
- Пересказать своё общее знание, а не найденные источники.

## Результат

На выходе — материал, готовый к передаче дальше:

1. Понимание темы с нескольких ракурсов.
2. Конкретные цифры и факты, каждый со ссылкой.
3. Реальные примеры и кейсы.
4. Позиции экспертов и авторитетные источники.
5. Тренды и контекст.
6. Ограничения и противоречия, включая те, что мешают удобной версии.

Для `consulting-analysis` это оформляется как **Data Package**: сводка данных по главам, ссылки для списка литературы, отметки о том, какие требования приоритета P0 закрыть не удалось. Отсутствующие данные помечаются явно, а не заполняются оценками.

Долгоживущий результат сохраняется по правилам vault: заметка в `База знаний/<категория>/` с frontmatter и записью в `База знаний/_Поисковый_индекс.md`; разовая справка — в `Ежедневник/YYYY-MM-DD.md`.
